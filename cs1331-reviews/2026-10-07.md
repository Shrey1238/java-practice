## 2. Today's concepts

### A. All four access levels (11.14)

| modifier | same class | same package | subclass (any package) | everyone |
|---|:-:|:-:|:-:|:-:|
| `private` | ✓ | | | |
| *(none)* — "default" / package-private | ✓ | ✓ | | |
| `protected` | ✓ | ✓ | ✓ | |
| `public` | ✓ | ✓ | ✓ | ✓ |

- **default** (no keyword): visible to any class in the **same package**. Forgetting `private` on a field gives you this, silently.
- **`protected`**: default **plus** subclasses in other packages. Intended for "things my subclasses need." Note it's *wider* than default, not narrower — a common misconception.
- Course guidance: fields stay `private`; give subclasses access through `protected` or `public` methods. Use `protected` fields sparingly (some HWs will tell you to).
- Top-level classes can only be `public` or default.

### B. Overriding (11.4–11.5)

A subclass **overrides** an inherited method by providing a new implementation with the **same signature** (name + parameter list).

```java
public class Animal {
    public String speak() { return "..."; }
}
public class Dog extends Animal {
    @Override                                  // ask the compiler to verify it really overrides
    public String speak() { return "Woof"; }
}
public class Puppy extends Dog {
    @Override
    public String speak() { return super.speak() + " (squeaky)"; }   // reuse the parent's version
}
```

Rules for a valid override:
1. Same method name and **exact same parameter list**.
2. Return type is the same (or a subtype — "covariant return").
3. Access level **cannot be more restrictive** (public → private is an error; protected → public is fine).
4. Cannot override `static`, `private`, or `final` methods (private ones aren't visible; static ones get *hidden*, not overridden — avoid).
5. Can't throw broader checked exceptions (later topic).

**Always write `@Override`.** If you make a typo (`Speak()`, or `speak(int)`), without the annotation you silently create a new overload; with it, the compiler errors. Free bug detection.

### C. Overriding vs. overloading — the exam favorite

| | Overriding | Overloading |
|---|---|---|
| where | subclass redefines parent's method | same class (or subclass) adds a method with the same name |
| parameter list | **identical** | **different** |
| decided at | **run time** (based on actual object) | **compile time** (based on argument types) |
| annotation | `@Override` | none |

```java
Animal a = new Dog();
a.speak();          // "Woof" — RUN-TIME type (Dog) decides → this is polymorphism (Oct 19 covers it fully)
```

### D. `super.` — calling the parent's version

`super.speak()` runs the parent implementation *on this object*. Typical uses: extending behavior rather than replacing it (`toString()` in a subclass often starts with `super.toString()`). You cannot chain `super.super.x()`.

## 3. Self-check (~5 min)

1. Is this an override, an overload, or an error?
   ```java
   class A { public void f(int x) {} }
   class B extends A { public void f(double x) {} }
   ```
   <details><summary>Answer</summary>Overload — different parameter type. <code>B</code> now has both <code>f(int)</code> and <code>f(double)</code>. Adding <code>@Override</code> would make it a compile error.</details>
2. Does this compile?
   ```java
   class A { public String name() { return "A"; } }
   class B extends A { @Override String name() { return "B"; } }
   ```
   <details><summary>Answer</summary>No — <code>String name()</code> (default access) is more restrictive than <code>public</code>.</details>
3. A field declared `int count;` (no modifier) in package `zoo` — can class `Vet` in package `clinic` read it? Can `Dog extends Animal` in package `clinic` read it?
   <details><summary>Answer</summary>No and no. Default access is same-package only; even subclasses outside the package can't see it (that's what <code>protected</code> would add).</details>
4. Output?
   ```java
   class A { public String hi() { return "A"; } }
   class B extends A { public String hi() { return "B" + super.hi(); } }
   A x = new B(); System.out.println(x.hi());
   ```
   <details><summary>Answer</summary><code>BA</code></details>
5. Why is `@Override` recommended even though it's optional?
   <details><summary>Answer</summary>It turns a silent mistake (accidental overload / typo) into a compile error.</details>
