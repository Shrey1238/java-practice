## 2. Today's concepts

### A. The problem DI solves

```java
public class TodoService {
    private final TodoRepository repo = new InMemoryTodoRepository();   // hard-wired dependency
}
```
`TodoService` *creates* its own dependency, so: you can't swap in a database repository without editing this class, and you can't test the service with a fake repository. **Tight coupling.**

### B. Dependency Injection — the fix (plain Java first)

```java
public class TodoService {
    private final TodoRepository repo;                 // depend on the INTERFACE
    public TodoService(TodoRepository repo) {          // dependency is handed in ("injected")
        this.repo = repo;
    }
}
// somewhere else decides which implementation:
TodoService s = new TodoService(new JpaTodoRepository());
```
This is pure CS 1331: interface + polymorphism + constructor parameter. DI is a *pattern*, not a Spring feature.

### C. Inversion of Control — who calls `new`?

Normally your code controls object creation. With IoC, the **framework** (the *container*) creates objects and wires dependencies; you just declare what you need. "Don't call us, we'll call you."

The Spring **IoC container** (`ApplicationContext`):
1. Scans your packages for annotated classes.
2. Creates one instance of each (a **bean**).
3. Looks at each bean's constructor parameters, finds matching beans, and passes them in.
4. Hands the fully-wired object graph to the app.

### D. Beans and the stereotype annotations

A **bean** = an object whose lifecycle the container manages. You mark classes to be picked up by component scanning:

| annotation | meaning |
|---|---|
| `@Component` | generic "make me a bean" |
| `@Service` | a component in the business-logic layer |
| `@Repository` | data-access component (adds exception translation) |
| `@Controller` / `@RestController` | web layer component |
| `@Configuration` + `@Bean` | a method whose *return value* becomes a bean (for classes you can't annotate, e.g. library types) |

```java
@Repository
public class InMemoryTodoRepository implements TodoRepository { ... }

@Service
public class TodoService {
    private final TodoRepository repo;
    public TodoService(TodoRepository repo) { this.repo = repo; }     // Spring injects the @Repository bean
}

@RestController
public class TodoController {
    private final TodoService service;
    public TodoController(TodoService service) { this.service = service; }   // and the @Service bean here
}
```

Facts:
- Default scope is **singleton**: one instance per container, shared everywhere. (So beans should generally be stateless — don't keep per-request data in fields.)
- Constructor injection is preferred; with a single constructor `@Autowired` is optional. You may also see `@Autowired` on fields (works, discouraged: not `final`, hard to test).
- Injection is **by type**: Spring looks for a bean assignable to the parameter type. Two candidates → error unless you disambiguate (`@Primary` / `@Qualifier("name")`). Zero → "No qualifying bean" startup failure.
- Component scanning starts from the `@SpringBootApplication` class's package downward — put controllers/services in **sub-packages** of it or they won't be found.

### E. Why this matters

- Swap `InMemoryTodoRepository` for `JpaTodoRepository` (Dec 2) by changing *which class has the annotation*, not the service.
- Unit-test `TodoService` with `new TodoService(new FakeRepository())` — no Spring needed. That's the payoff of constructor injection.

## 3. Self-check (~5 min)

1. Define DI vs IoC in one line each.
   <details><summary>Answer</summary>DI: a class receives its dependencies from outside instead of constructing them. IoC: the framework, not your code, controls object creation and wiring — DI is how Spring implements IoC.</details>
2. Why depend on `TodoRepository` (interface) rather than `InMemoryTodoRepository`?
   <details><summary>Answer</summary>Polymorphism — any implementation can be injected without changing the dependent class.</details>
3. Two classes implement `TodoRepository`, both annotated `@Repository`. What happens at startup?
   <details><summary>Answer</summary>Ambiguity error ("expected single matching bean but found 2") unless one is <code>@Primary</code> or the injection point uses <code>@Qualifier</code>.</details>
4. You put `TodoService` in package `com.other.services` while the app class is in `edu.gatech.todo`. Symptom?
   <details><summary>Answer</summary>Not scanned → no bean → controller fails to start with "No qualifying bean of type TodoService".</details>
5. Is a `@Service` bean created once or per request by default?
   <details><summary>Answer</summary>Once — singleton scope.</details>
